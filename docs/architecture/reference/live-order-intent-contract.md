# LIVE order intent and unknown outcome

## Submission contract

For a LIVE order, `openOrder` commits `LiveOrderIntent` before any exchange `createOrder` call. The intent stores a unique venue `clientOrderId`, user, venue, symbol, original command and fingerprint. Its UUID becomes the local `Order.id`. A repeated request with the same client ID and fingerprint reads the existing order or queries the exchange; it never sends another `createOrder`. A different manual command with the same client ID fails with `LIVE_INTENT_CONFLICT`. Runtime retries may have a new sampled price or quantity; if all other command fields still match, the retry uses the persisted original quantity and price for lookup and local materialization.

The exchange adapter calls `createOrder` once, regardless of the legacy retry-policy input. If submission throws or returns no exchange order ID, the service queries by the same client ID. A successful lookup commits the local Order, immediate OPEN position lifecycle, and fill rows in one database transaction. A crash or database error before that commit leaves the intent unresolved for a lookup-only retry. A missing, failed, unsupported, or terminal-state lookup returns `LIVE_EXECUTION_UNKNOWN` with the intent/order ID and client ID. The intent remains durable. This response does **not** mean the order was rejected or never reached the exchange. A later retry with the same ID repeats only the lookup. Runtime deduplication allows this lookup retry. Pretrade errors known to occur before submission remove the unused intent and preserve their original error.

When an adapter fill has no exchange trade ID, materialization assigns a deterministic synthetic ID from the order symbol, side, fill price, quantity, and occurrence among economically identical fills. Fee, timestamp, and raw payload do not define the ID; reordered snapshots retain the same set of IDs. For economically identical rows, the occurrence tracks multiplicity rather than an individual venue fill. The `(orderId, exchangeTradeId)` index keeps distinct rows and rejects duplicate identities. Once the Order transaction commits, retrying the same intent returns its existing Order and fills.

The fee reconciliation adapter compares indistinguishable fills without exchange trade IDs against the exchange's cumulative filled quantity. A quantity that proves two executions preserves both rows; a quantity that proves one collapses a repeated snapshot. If any preserved fill still lacks a fee, the fee remains pending and no complete effective rate is reported. Missing or inconsistent quantity evidence returns `LIVE_EXECUTION_UNKNOWN` with the intent still unresolved. `openOrder` also rejects a FILLED snapshot whose available fill quantities contradict the requested quantity, instead of persisting a false partial fill. This is source-level and isolated-test behavior, not exchange or production acceptance.

The CCXT normalizer keeps a missing fee as `null`; an explicit exchange fee of zero remains `0`. Immediate LIVE position materialization preserves `feePending` on the Order. A later exchange fee event can fill a single matching unresolved synthetic OrderFill by price and quantity without replacing its ID or creating a second fill. If multiple synthetic fills match, the fee stays pending for reconciliation. Read-only imported position history also declines to derive financial results from a trade with an unknown fee.

For an immediate runtime DCA or CLOSE fill, Order and fill rows commit first. The runtime then commits Position, Trade, and successful dedupe state together under a per-order transaction lock. A crash between these commits leaves the position unchanged and the order recoverable by its original client ID; a retry reads the existing order and finishes the transaction. A crash within the finalization transaction rolls back Position, Trade, and dedupe together. The Trade row is the durable completion evidence: a filled Order or an existing Position alone does not complete DCA/CLOSE. Runtime DCA records `LIVE_EXECUTION_UNKNOWN` as retryable and audits it, while later retries remain lookup-only. Order/fill writes, finalization, and telemetry remain separate commits; this is not a claim that exchange submission and all local effects share one transaction.

When the normalized Binance fill handler is called, it locks the exchange order identity and commits the Order status, unique OrderFill row, Position, and Trade in one database transaction. A replay of the same fill can repair an older Order left FILLED before its fill or lifecycle was recorded, using the persisted exchange trade ID and accepted cumulative quantity; it does not submit another exchange order. The runtime dedupe and Redis state update happen after the database commit and can be completed by replay. A unique `(orderId, exchangeTradeId)` index rejects duplicate local fills; its migration aborts when existing duplicates need reviewed reconciliation. The API and execution worker startup do not instantiate `BinanceUserDataStreamService` or call this handler. Tests prove the callable handler, not a running stream or eventual fill recovery after restart. Polling reconciliation of local active LIVE orders and unresolved intents is a separate required integration for Binance and Gate Spot/Futures.

Runtime-generated IDs remain unchanged on Binance. Gate.io uses a deterministic 27-character `soar_` ID derived from the runtime ID; CCXT adds the required `t-` prefix for Spot and Futures. The manual order UI sends one request-scoped ID and retains it in browser storage for the same form after an error or reload. A successful response clears it. API clients can send `clientOrderId` directly and should reuse it for retries.

## Venue limits and operator handling

The venue ID is a lookup key, not a permanent exchange-side idempotency guarantee. Binance's Futures `newClientOrderId` is unique among open orders; historical order queries have retention limits. Gate.io custom `text` IDs are prefixed `t-` and have length and query-window limits. Gate Spot's single-order lookup by custom `text` works only while an order is pending; once filled or canceled, it requires the numeric exchange order ID. Its finished-order list supports time-bounded pagination and includes `text`, but this change does not implement a complete, account-scoped, paginated history recovery. A quick Gate Spot fill after a lost response therefore stays `LIVE_EXECUTION_UNKNOWN` and requires operator reconciliation. A `not found` response never authorizes resubmission. Inspect the exchange account/order history and the durable intent before taking a new trading action. The pending intent is not deleted automatically.

Source contracts: [Binance Spot trading REST](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/trade), [Binance USD-M Futures trading REST](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade), [Gate.io Spot API](https://www.gate.com/docs/developers/apiv4/en/spot/), [Gate.io Futures API](https://www.gate.com/docs/developers/apiv4/en/futures/).

## Rollout and verification

Deploy the additive Prisma migrations before the API code. Before the unique `(userId, exchangeOrderId)` index, run `node apps/api/scripts/preflight-live-order-identity.mjs` with the target database URL and reconcile any duplicate pairs under review. The migration repeats this preflight and aborts before index creation if duplicates remain. The index is conservative across venues because historical Order rows have no venue column: an ID collision across venues fails closed and requires operator review. Existing orders need no payload backfill; older intents without stored payload still support exact-command lookup, while a changed runtime command conflicts. Do not roll back to API code that can submit LIVE orders without consulting unresolved intents. First disable LIVE submission, inventory and reconcile unresolved intents against exchange history, and verify a schema-compatible rollback candidate that preserves lookup-only recovery. Do not drop the intent table while unresolved intents exist.

For the OrderFill index, run `node scripts/preflight-order-fill-identity.mjs` from `apps/api`. It checks only an isolated `_test` database selected by `TEST_DATABASE_URL` or a localhost runtime URL with `_test` appended. It reports duplicate `(orderId, exchangeTradeId)` groups without changing rows. The migration independently checks the target database and fails before index creation if duplicates exist. No duplicate rows are removed automatically.

The local order insert and periodic open-order importer serialize on the same PostgreSQL advisory transaction lock for a user and exchange order ID. The importer checks all orders for that user and exchange ID, even after bot or wallet reassignment, and the unique database index guards other writers. If an exchange snapshot already imported an order after a lost response, the intent stays unresolved and returns `LIVE_EXECUTION_UNKNOWN` rather than creating another local order. An operator must reconcile the imported row and intent before declaring the command complete.

Validation uses the isolated `_test` database and mocked exchange clients: accepted-but-timeout, unresolved timeout followed by restart/retry, single submit, Binance/Gate Spot/Futures ID mapping, and manual UI reuse of a client ID. A real signed-in LIVE read/submit flow and exchange-history reconciliation were not executed by this change; they require a separately authorized safe environment. Until then, this is code and isolated-test evidence, not production acceptance.
