# LIVE order intent and unknown outcome

## Submission contract

For a LIVE order, `openOrder` commits `LiveOrderIntent` before any exchange `createOrder` call. The intent stores a unique venue `clientOrderId`, user, venue, symbol, original command and fingerprint. Its UUID becomes the local `Order.id`. A repeated request with the same client ID and fingerprint reads the existing order or queries the exchange; it never sends another `createOrder`. A different manual command with the same client ID fails with `LIVE_INTENT_CONFLICT`. Runtime retries may have a new sampled price or quantity; if all other command fields still match, the retry uses the persisted original quantity and price for lookup and local materialization.

The exchange adapter calls `createOrder` once, regardless of the legacy retry-policy input. If submission throws or returns no exchange order ID, the service queries by the same client ID. A successful lookup commits the local Order, immediate OPEN position lifecycle, and fill rows in one database transaction. For a runtime-generated LIVE OPEN with a runtime session, that transaction also commits the Trade, runtime event, symbol stat, known fee settlement, and successful dedupe state. A crash or database error before that commit leaves the intent unresolved for a lookup-only retry. A missing, failed, unsupported, or terminal-state lookup returns `LIVE_EXECUTION_UNKNOWN` with the intent/order ID and client ID. The intent remains durable. This response does **not** mean the order was rejected or never reached the exchange. A later retry with the same ID repeats only the lookup. Runtime deduplication allows this lookup retry. Pretrade errors known to occur before submission remove the unused intent and preserve their original error.

When an adapter fill has no exchange trade ID, materialization assigns a deterministic synthetic ID from the order symbol, side, fill price, quantity, and occurrence among economically identical fills. Fee, timestamp, and raw payload do not define the ID; reordered snapshots retain the same set of IDs. For economically identical rows, the occurrence tracks multiplicity rather than an individual venue fill. The `(orderId, exchangeTradeId)` index keeps distinct rows and rejects duplicate identities. Once the Order transaction commits, retrying the same intent returns its existing Order and fills.

The fee reconciliation adapter compares indistinguishable fills without exchange trade IDs against the exchange's cumulative filled quantity. A quantity that proves two executions preserves both rows; a quantity that proves one collapses a repeated snapshot. If any preserved fill still lacks a fee, the fee remains pending and no complete effective rate is reported. Missing or inconsistent quantity evidence returns `LIVE_EXECUTION_UNKNOWN` with the intent still unresolved. `openOrder` also rejects a FILLED snapshot whose available fill quantities contradict the requested quantity, instead of persisting a false partial fill. This is source-level and isolated-test behavior, not exchange or production acceptance.

The CCXT normalizer keeps a missing fee as `null`; an explicit exchange fee of zero remains `0`. Immediate LIVE position materialization preserves `feePending` on the Order. A later exchange fee event can fill a single matching unresolved synthetic OrderFill by price and quantity without replacing its ID or creating a second fill. If multiple synthetic fills match, the fee stays pending for reconciliation. Read-only imported position history also declines to derive financial results from a trade with an unknown fee.

For an immediate runtime DCA or CLOSE fill, Order and fill rows commit first. The runtime then commits Position, Trade, runtime event, symbol stat, known financial settlement, and successful dedupe state together under a per-order transaction lock. A crash between these commits leaves the position unchanged and the order recoverable by its original client ID; a retry reads the existing order and finishes the transaction. A crash within the finalization transaction rolls back these effects together. The Trade row is the durable completion evidence: a filled Order or an existing Position alone does not complete DCA/CLOSE. Runtime DCA records `LIVE_EXECUTION_UNKNOWN` as retryable and audits it, while later retries remain lookup-only. Exchange submission and local database effects do not share a transaction.

Runtime OPEN persistence and the Binance event handler acquire the same PostgreSQL advisory transaction lock keyed by user and exchange order ID before checking the Trade. This lock works across API and worker processes using separate database connections. It prevents the two writers from both observing an absent OPEN Trade and event. The runtime path fails closed if its local Order lacks an exchange order ID or already has multiple OPEN Trades. Existing historical duplicates or partially written telemetry still require the [audited repair plan](../../operations/live-runtime-telemetry-repair-plan.md).
An older unresolved runtime intent may lack a stored session ID. A new lookup-only retry can supply the current session while retaining the original quantity and price. A FILLED runtime intent without any valid session fails closed before Position is committed; it remains unresolved for later review or retry. This does not repair Orders that were already committed by older code.

When the normalized Binance fill handler is called, it locks the exchange order identity and commits the Order status, unique OrderFill row, Position, and Trade in one database transaction. A replay of the same fill can repair an older Order left FILLED before its fill or lifecycle was recorded, using the persisted exchange trade ID and accepted cumulative quantity; it does not submit another exchange order. The runtime dedupe and Redis state update happen after the database commit and can be completed by replay. A unique `(orderId, exchangeTradeId)` index rejects duplicate local fills; its migration aborts when existing duplicates need reviewed reconciliation. The API and execution worker startup do not instantiate `BinanceUserDataStreamService` or call this handler. Tests prove the callable handler, not a running stream or eventual fill recovery after restart. Polling reconciliation of local active LIVE orders and unresolved intents is a separate required integration for Binance and Gate Spot/Futures.

Runtime-generated IDs remain unchanged on Binance. Gate.io uses a deterministic 27-character `soar_` ID derived from the runtime ID; CCXT adds the required `t-` prefix for Spot and Futures. The manual order UI sends one request-scoped ID and retains it in browser storage for the same form after an error or reload. A successful response clears it. API clients can send `clientOrderId` directly and should reuse it for retries.

## Venue limits and operator handling

### SOAR-LIVE-FILL-RECON-001 stage 1 (read-only preparation)

`findLiveFillCandidatePage` reads unresolved intents and local LIVE orders with open, partial, or incomplete filled/fee state from durable database rows. For a FILLED order it also compares the database sum of `OrderFill.quantity` with `Order.filledQuantity`, using a conservative floating-point tolerance scaled to the stored quantity; a missing fraction remains a candidate even if a fill, Trade, and resolved fee already exist. FILLED with zero or invalid filled quantity is selected for diagnosis, and lookup returns `UNKNOWN` before venue I/O. No symbol quantity step is persisted on Order, so this tolerance covers numeric roundoff rather than asserting venue-level precision. The selector returns separate intent and order cursors for a later worker. `lookupLiveFillCandidate` reads the venue by the persisted numeric order ID first, then the client ID. For Gate Spot and Futures, a failed client-ID lookup can inspect a bounded 24-hour history window (at most three 100-order pages) and accepts only one exact account, symbol, side, and client-ID match. Gate Spot uses finished-order pages; Gate Futures uses the time-range endpoint with offset pagination. Absence, conflicting IDs, truncated history, venue errors, missing provenance, or changed bot, wallet, or API-key bindings return `UNKNOWN` and never cause a new `createOrder`.

The current intent payload does not persist the exact API-key ID selected during submission. Stage 1 therefore uses the original intent's venue/market plus unchanged bot, wallet, and key rows; any row updated after intent creation fails closed. Legacy local orders without an intent are surfaced as candidates but cannot be looked up automatically. This conservative check may leave genuine orders `UNKNOWN` after unrelated account edits. The lookup result is a read-only data interface for a later transaction finalizer. No worker, timer, stream, financial write, deployment, or production acceptance is included in this stage.

### SOAR-LIVE-FILL-RECON-001 stage 2 (explicit recovery only)

`recoverLiveFillCandidateOnce` performs one explicit lookup and accepts only a FOUND order with a consistent venue-filled quantity, complete order-scoped fill evidence, stable fill identities, and one fee currency. Missing or ambiguous evidence returns UNKNOWN before a database write. Within one transaction it rechecks the intent, account provenance, local order identity, exchange order ID, and existing local fill economics under the shared advisory lock. It then creates a still-unresolved local Order if needed and replays the verified fills through the same transaction body as the exchange event handler. The last complete fill finalizes Position and Trade through the existing OPEN/DCA/CLOSE paths; fee and PnL remain nullable until the exchange provides complete fee evidence. Runtime event, symbol statistic, and matched dedupe state are written with the order effects. A failure during the batch rolls back all database effects; replay uses fill identities and the same lock.

The lookup may use an order-scoped trade read when the order snapshot lacks fill rows. This read is capped at 1000 trades; an incomplete result remains UNKNOWN in the finalizer. An already FILLED local Order without exactly one lifecycle Trade stays UNKNOWN, because a historic Position write without Trade cannot prove whether applying the lifecycle again would double the position. After the database commit, explicit recovery follows the event handler's DCA runtime-state synchronization or invalidates a closed position's runtime state. Redis cannot join the database transaction: a crash or failed cache write is surfaced for replay, while the console and automation reject BOT cache values whose quantity or entry differs from the canonical Position; closed BOT positions never use cached state. Stage 2 by itself included no timer, worker polling, lease, restart hook, Binance stream, deployment, or real exchange execution. A legacy local Order without an intent lacks proven original account provenance and remains UNKNOWN.

### SOAR-LIVE-FILL-RECON-001 stage 3 (execution-worker polling)

The execution worker starts `LiveFillRecoveryLoop` at boot and stops it on SIGINT/SIGTERM. One Redis lease token owns a scan cycle across processes; renewal, release, cursor writes, and pending-candidate writes compare that token. A process that loses ownership does not begin finalization. The stage-2 transaction and exchange-order advisory lock remain the database idempotency boundary if a lease expires while a finalizer is already committing. Each cycle reads at most two pages of five intent/order rows by default, uses durable cursors across process restarts, spaces venue reads by at least one second, times out a waiting lookup after 20 seconds, and applies capped Redis cooldown/backoff to UNKNOWN and failures. Only FOUND reaches the finalizer. No path submits a replacement exchange order.

Before finalization the worker saves the candidate in a Redis pending set. It removes the marker only after the database and runtime-cache paths succeed; a new process retries a marker left by a crash after database commit. This is process-restart recovery, not a guarantee against loss of Redis itself. If Redis loses that marker after a fully settled fill, the stage-1 selector may no longer emit that order. The console and automation still compare BOT cache values with canonical Position data, and a closed position cannot use cached state, but automatic cache repair after Redis data loss is not proven. No Binance user stream, actual exchange order, production deployment, or signed-in acceptance is part of this stage.

### SOAR-LIVE-FILL-RECON-001 stage 4 (Binance user stream)

The execution worker also starts the Binance user-stream loop and drains it before shutting down the polling loop. Eligible subscriptions are unique Binance API-key/market pairs from opted-in LIVE bots, including inactive bots that can receive late fills, and LIVE wallets for manual orders. A bounded scan refreshes these bindings and closes a session when the account is unlinked or its key changes. Redis token leases permit one stream owner per pair across worker processes; a lost owner stops applying events. Each account has a capped reconnect backoff, connection deadline, ping/pong check, and (Futures) listenKey keepalive. Spot uses Binance's signed WebSocket API subscription because its REST listenKey route is retired; Futures uses its REST listenKey and private stream path. Neither path submits an order.

Normalized events enter the existing transactional order/account handler with the source API-key ID. Order events require that ID to match the currently bound bot or wallet key before any domain write; the shared exchange-order lock, fill identity, Trade and runtime-event checks remain the idempotency boundary for a stream/poll/replay race. Polling continues independently when the stream is disconnected. The admin-only `/workers/live-execution` endpoint reports aggregate connection freshness, reconnects/errors and polling UNKNOWN/pending counts and oldest pending age from Redis; `/workers/ready` returns `not_ready` for a missing, stale, or disconnected stream or recovery status in split-worker mode. The public API `/ready` reports only API dependencies. These states contain no key material or listenKey. A quiet account's last event time is observational; a current ping/pong and lease state are the connection liveness checks. Older execution workers do not honor the stream lease, so a future deployment requires stop-before-start and a fresh worker-readiness check.

Futures `ACCOUNT_UPDATE` can arrive before or after its `ORDER_TRADE_UPDATE`. For BOT/USER-origin positions it observes account quantity and entry price but never writes them to the fill-backed Position; a mismatch, including a zero snapshot before CLOSE, records `RECOVERING` diagnostics while leaving `syncState=IN_SYNC` so the matched fill can finalize. Duplicate or older account snapshots cannot repeat that diagnostic. The DCA fill keeps the newest account observation timestamp and clears the diagnostic in its transaction. Imported `EXCHANGE_SYNC` positions retain their separate account-snapshot update contract. The stream therefore cannot count a DCA fill on top of an account quantity already changed by the same fill.

Local isolated-database/Redis tests simulate start, stop, reconnect, restart takeover, unavailable socket, and a stream/poll/duplicate DCA race. They do not establish venue connectivity, real LIVE fill correctness, deployed worker health, or signed-in production acceptance. Selective loss of Redis pending metadata after a fully settled DB commit can leave older BOT runtime cache in place even though the console rejects it. The separate reproducible task is `history/tasks/live-fill-cache-repair-after-redis-loss-2026-10-18-task.md`; this stage does not claim automatic repair of that case. See Binance's [Spot WebSocket API user-stream subscription](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/user-data-stream) and [USDⓈ-M Futures user-stream connection contract](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/user-data-streams).

The venue ID is a lookup key, not a permanent exchange-side idempotency guarantee. Binance's Futures `newClientOrderId` is unique among open orders; historical order queries have retention limits. Gate.io custom `text` IDs are prefixed `t-` and have length and query-window limits. Gate Spot's single-order lookup by custom `text` works only while an order is pending; once filled or canceled, it requires the numeric exchange order ID. Its finished-order list supports time-bounded pagination and includes `text`. The existing `openOrder` retry still uses only the single-order lookup, so a quick Gate Spot fill after a lost response remains `LIVE_EXECUTION_UNKNOWN` on that path. The stage-1 lookup can identify the order in bounded history, and the stage-3 worker invokes the stage-2 finalizer only for FOUND. A `not found` response never authorizes resubmission. Inspect the exchange account/order history and the durable intent before taking a new trading action. The pending intent is not deleted automatically.

Source contracts: [Binance Spot trading REST](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/trade), [Binance USD-M Futures trading REST](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade), [Gate.io Spot API](https://www.gate.com/docs/developers/apiv4/en/spot/), [Gate.io Futures API](https://www.gate.com/docs/developers/apiv4/en/futures/).

## Rollout and verification

Deploy the additive Prisma migrations before the API code. Before the unique `(userId, exchangeOrderId)` index, run `node apps/api/scripts/preflight-live-order-identity.mjs` with the target database URL and reconcile any duplicate pairs under review. The migration repeats this preflight and aborts before index creation if duplicates remain. The index is conservative across venues because historical Order rows have no venue column: an ID collision across venues fails closed and requires operator review. Existing orders need no payload backfill; older intents without stored payload still support exact-command lookup, while a changed runtime command conflicts. Do not roll back to API code that can submit LIVE orders without consulting unresolved intents. First disable LIVE submission, inventory and reconcile unresolved intents against exchange history, and verify a schema-compatible rollback candidate that preserves lookup-only recovery. Do not drop the intent table while unresolved intents exist.

For the OrderFill index, run `node scripts/preflight-order-fill-identity.mjs` from `apps/api`. It checks only an isolated `_test` database selected by `TEST_DATABASE_URL` or a localhost runtime URL with `_test` appended. It reports duplicate `(orderId, exchangeTradeId)` groups without changing rows. The migration independently checks the target database and fails before index creation if duplicates exist. No duplicate rows are removed automatically.

The local order insert and periodic open-order importer serialize on the same PostgreSQL advisory transaction lock for a user and exchange order ID. The importer checks all orders for that user and exchange ID, even after bot or wallet reassignment, and the unique database index guards other writers. If an exchange snapshot already imported an order after a lost response, the intent stays unresolved and returns `LIVE_EXECUTION_UNKNOWN` rather than creating another local order. An operator must reconcile the imported row and intent before declaring the command complete.

Validation uses the isolated `_test` database and mocked exchange clients: accepted-but-timeout, unresolved timeout followed by restart/retry, single submit, Binance/Gate Spot/Futures ID mapping, and manual UI reuse of a client ID. A real signed-in LIVE read/submit flow and exchange-history reconciliation were not executed by this change; they require a separately authorized safe environment. Until then, this is code and isolated-test evidence, not production acceptance.
